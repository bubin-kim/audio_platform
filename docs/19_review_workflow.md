# 19. 검수 절차 — 자동 커팅 결과를 사람이 확인하기

> 상태: **운영 절차 (v1.0, 2026-08-13)**
> 대상: 이벤트 검출 커팅(`event_detection`)으로 만든 데이터셋을 쓰는 연구원.

## 왜 검수가 필요한가

자동 탐지는 **완벽하지 않다**. 파일럿 실측 성능:

| 파일 | 조각 | 진짜(TP) | 헛것(FP) | 놓침(FN) |
|---|---|---|---|---|
| 파일럿_004 | 31개 | 24 | **7** | 7 |
| 파일럿_005 | 32개 | 28 | **4** | 7 |

즉 **조각 10개 중 1~2개는 경보음이 아니다.** 그대로 학습에 쓰면 라벨이
오염된다. 왜 이 이상 자동화가 어려운지는 docs/17 §2g에 실측으로 남겼다 —
요약하면 오탐이 진짜 경보음보다 신호가 더 강해서, 임계값으로는 못 가른다.

## 검수 절차 (조각 1개당 10~20초)

**https://audio-platform-eta.vercel.app** → 프로젝트 → 데이터셋 → 세그먼트 표

1. **▶ 재생** — 목표 소리(경보음 등)가 들리는가?
2. **스펙트로그램** — 안 들리면 눈으로 확인. 해당 대역(경보음이면 2kHz 부근)에
   밝은 무늬가 있는지 본다.
3. **판정**
   - 들린다 → 그대로 둔다 (필요하면 라벨 입력)
   - 안 들린다/다른 소리 → **삭제**
4. 원본 위치 칸의 `(탐지 N초)`는 원본 어디를 잡았는지다. 의심스러우면 원본
   파일 섹션의 전체 파형·스펙트로그램에서 그 지점을 확인한다.

### 판정이 애매할 때

- **소리는 약한데 스펙트로그램에 대역 무늬가 보인다** → 진짜일 가능성이 높다.
  환경음에 묻힌 이벤트는 귀보다 스펙트로그램이 잘 보여준다(docs/16).
- **조각 한가운데(3초 지점)가 아니라 시작·끝에서 들린다** → 탐지 시각이 어긋난
  것이다. 소리 자체가 목표음이면 남겨도 되지만, 학습에 위치 일관성이 중요하면
  삭제하고 재커팅을 고려한다.
- **조각 길이가 6초가 아니다** → 파일 경계에 걸린 것이다. 특히 **맨 앞 조각**은
  구조적으로 오탐이 잦다: 분석 시작 프레임은 "평소 수준"을 뒤쪽만 보고 계산해
  실제보다 크게 튄 것처럼 보인다(docs/17 §2h). 파일럿 005의 첫 조각(3.09초)이
  그 사례였고, 경보음이 없었다.
  → **길이가 다른 조각은 우선 확인 대상**으로 삼는다. 다만 파일 끝 조각은
  진짜인 경우가 많으니(파일럿 2개 모두 183~184초에 실제 경보음) 반드시 들어본다.

## 검수 결과를 성능 수치로 만들기 (선택)

검수하면서 "몇 초에 진짜가 있었나"를 적어두면 GT가 된다. GT가 있으면
파라미터를 바꿀 때마다 성능을 재볼 수 있다:

```bash
cd backend
# backend/gt/새파일.json 을 만든 뒤 (형식은 gt/README.md)
uv run python scripts/evaluate_detection.py \
    --audio <원본경로> --gt gt/새파일.json --detail
```

이렇게 쌓인 GT는 나중에 분류기를 학습시킬 때 그대로 쓰인다.

## 알아둘 것

- **삭제는 되돌릴 수 없다.** 조각 파일과 DB 행이 함께 지워진다.
- 검수로 조각을 지우면 대시보드 수집 진행률(개수)이 내려간다 — 정상이다.
- 놓친 이벤트(FN)는 조각 자체가 없으므로 검수 화면에 나타나지 않는다.
  전체를 다 담아야 하는 연구라면 원본 파형·스펙트로그램을 훑어 확인한다.
- 조각에는 `_detection` 메타데이터(원본명·탐지시각·prominence·대역·임계·채널)가
  자동 저장된다. CSV export에는 나오지 않지만 API로 조회할 수 있다.
