# 16. 스펙트로그램 시각화 + 원본 섹션 (V2-8)

> 상태: **설계안 (v1.0, 2026-08-04)** — 사용자 결정 반영: 원본 표시 위치=데이터셋
> 상세에 원본 섹션 신설, 주파수 축=로그(멜) 스케일.
> 배경: 환경음에 묻힌 이벤트(예: 260804_005.WAV의 경적)가 웨이브폼에는 안 보이지만
> 스펙트로그램의 대역 에너지로는 보인다 — 수집 현장에서 녹음 품질을 눈으로 판단하는 도구.

## 1. 목표와 범위

- **A. 원본 스펙트로그램**: 데이터셋 상세에 **"원본 파일" 섹션 신설** — 파일명·업로더
  (V2-7 잔여 해소)·길이 목록 + 행마다 통 음원 스펙트로그램. 업로드 직후에는 기존
  "데이터셋으로 이동" 링크로 도달한다.
- **B. 세그먼트 스펙트로그램**: 세그먼트 테이블의 기존 미니 파형 **옆에** 같은 크기의
  미니 스펙트로그램.
- 주파수 축은 **멜(로그) 스케일** — 저음(심음)~고음 도메인 전부에서 유효, 도메인
  전용 설정 없음(P1). 표시 상한은 파일의 나이퀴스트(sr/2)를 그대로 따른다.

**비목표**: 재생 위치 커서 연동, 확대/구간 선택, 스펙트로그램 기반 커팅(별도 제안),
서버측 PNG 렌더(새 의존성 금지 — matplotlib 불필요).

## 2. 아키텍처 (기존 waveform 패턴 그대로)

```
audio/spectrogram.py (순수 계산, librosa)  ← P2: web/DB import 없음
  → services/… (storage.local_path로 파일 접근)
  → api: GET /segments/{id}/spectrogram · GET /source-files/{id}/spectrogram
  → frontend: <Spectrogram> 캔버스 렌더 (JSON 수신 → 컬러맵)
```

- 계산: `librosa.feature.melspectrogram` → dB 변환 → **0~100 uint8 양자화** →
  base64 문자열로 응답 (3분 원본 ≈ 800열×96멜 ≈ 77KB — JSON 2D 배열 대비 1/6).
- 열 수는 길이에 비례하되 상한: 원본 max 800열, 세그먼트 max 240열.
- 파일 불변 → `Cache-Control: private, max-age=3600` (waveform과 동일).
- 인증: api.ts `request()` 경유(XHR + Bearer 헤더)라 쿼리 토큰 불필요.

## 7. 비프 대역 확대 탭 + 대역통과 검출기 (2026-08-28, 표시 전용 신규 기능)

차량 비프음(차키 리모컨, 1900~2100Hz 협대역)이 저역 배경(엔진·환기팬·음악)에
묻혀 §1~6의 전대역 멜 스펙트로그램·평균+Nσ 피크 검출로는 안 보이던 문제를
표시 전용 새 기능으로 보완했다. **기존 기능(파형·실제 크기·배경 제거 탭,
피크 검출, 세그먼트 컷팅)은 전혀 수정하지 않았다** — 전부 새 파일로 분리.

**추가 1: 대역통과 기반 onset 검출** (`app/audio/band_beep_detector.py`)
```
채널 평균 → butterworth 4차 대역통과(filtfilt, 기본 1800~2200Hz)
→ Hilbert 엔벨로프 → 짧은 스무딩 → 지역 적응형 임계값(±2초 median+k*MAD)
→ find_peaks(distance=min_gap_sec)
```
`k` 기본값은 최초 사양 5가 아니라 **8** — 합성 신호 실측(저역 배경잡음 +
1900~2100Hz 톤 10개)에서 k=5는 오탐 25개(배경 요동이 지역 MAD의 5배를
자주 넘음), k=8부터 진짜 10개가 정확히 잡히고 오탐이 파일 경계(filtfilt
트랜지언트) 2개로 줄었다 — 실측 기반 채택, 추측으로 사양값을 그대로 쓰지
않았다.

**경계 오탐 결함과 수정(전역 하한 `k_global`)**: 지역 임계값만 쓰면 파일
맨앞·맨끝에서 오탐이 남았다. 원인은 `ndimage.median_filter(mode="nearest")`
가 경계에서 가장자리 값을 복제해 **지역 MAD가 거의 0**이 되는 것
(실측: 파일 끝에서 0.0000007 — 진짜 onset 지점의 1/25). 임계값이
비정상적으로 낮아져 진짜 신호의 1/5 크기 잡음도 통과했다. **k를 올려도
안 고쳐진다** — 경계는 지역 통계 자체가 무너진 것이라 배수를 키우면
임계값도 같이 낮게 유지되고, 오히려 k=16부터 진짜 비프음을 놓쳤다(실측).
해결: `max(지역임계값, 전역median + k_global*전역MAD)`로 절대 하한을
함께 건다. `k_global=8`은 합성 100초(경계 오탐 2개만 정확히 제거, 진짜
10개 유지)와 **실제 NAS 세그먼트 3개**(각 1개씩만, 기대 3.0초 대비 오차
15ms 이내) 양쪽으로 검증. `k_global=0`이면 이 하한이 꺼진다.

**추가 2: 주파수 크롭 스펙트로그램** (`app/audio/band_spectrogram.py`)
선형 STFT(n_fft=4096, hop_length=512, hann) → `amplitude_to_db(top_db=60)`
→ [fmin, fmax](기본 1500~2500Hz)만 세로 전체 높이로 크롭. 계산은 정밀
해상도 그대로 하고 **응답 직전에만** 열을 `max_cols`(기본 800)로
다운샘플링(구간 최대값 — 짧은 비프음이 평균으로 흐려지지 않게, §2i와
같은 이유)해 페이로드를 1MB대에서 90KB대로 줄였다.

**추가 3: 순음성(tonality) 필터 — 오탐 제거** (2026-08-28)

엔벨로프 크기만으로는 실제 주차장 환경의 광대역 소리(문 닫힘·차량
통과·반향)가 대역 안 에너지를 튀게 해 오탐이 된다. NAS 실원본
(`260818_001.WAV`, 100초)에서 검출 20개 중 **진짜 10 + 오탐 10**이었다.

두 무리를 스펙트럼으로 재보니 완전히 갈렸다:

| | 피크 주파수 | 대역 안 최대 / 대역 밖 평균 |
|---|---|---|
| 진짜 10개 | **전부 1992Hz** | 14.9~19.3 dB |
| 오탐 10개 | 1922~2086Hz 흩어짐 | 2.0~11.8 dB |

그래서 후보마다 `scipy.signal.welch`로 스펙트럼을 보고 **대역 안 최대
파워가 대역 밖(300~1500Hz, 2600~6000Hz) 평균보다 `tonality_db` 이상
큰 것만** 남긴다. 임계값은 실제 구현으로 스윕해 **14dB** 채택 —
12~13dB는 오탐 1~2개 잔존, 16dB부터 진짜를 놓치기 시작(9/10).

**결과**: 실데이터 진짜 10/10·오탐 **0개**(오프셋 표준편차 0.08초,
간격 9.80~10.14초), 합성 100초도 10개 유지. NAS 실서버 배포·브라우저
확인 완료.

**추가 5: 주기 누적 모드 — 임계값 방식의 근본 한계 해결** (2026-08-28)

**1일차 54개 전수 검증에서 임계값 방식이 무너졌다**: 정상 7개(13%),
0개 검출 12개, 1~5개 24개. 파일 하나(260818_001)로 튜닝한 것이 원인
이었다 — 그 파일만 신호가 강했고, 거리·각도가 다른 파일은 **진짜
비프음이 잡음 상위값보다 작았다**(분리 여유 0.25~0.84배).

파라미터 100개 조합(k×k_global×tonality_db)을 9개 파일 GT로 **전수
스윕한 결과 최선이 F1 65.1%**(TP57/FP28/FN33) — 어떤 임계값으로도
해결 불가능함을 수치로 확인했다.

**해결: 임계값을 버리고 주기를 쓴다.** 녹음 설계상 비프음은 10초마다
울린다. 100초를 10초씩 접어 누적하면 신호는 10배로 쌓이고 잡음은
√10배만 커진다(접은 곡선 대비 3.7~64배 실측). 접은 곡선의 최대점이
위상이고, 각 주기 창에서 최대점을 하나씩 고른다 — **임계값이 아예
필요 없으므로** 신호가 잡음에 묻혀 있어도 위치를 찾는다.

`period_sec` 기본값은 0(꺼짐) — 주기를 모르는 데이터에는 안 켜진다.
프론트는 이 프로젝트 녹음이 10초 주기이므로 10으로 켜서 호출한다.

**추가 6: 위상 판정에 원형(circular) 표준편차** (2026-08-28)

주기 모드 도입 후 51/54가 됐는데, 남은 3개는 **검출이 아니라 판정
지표가 틀린 것**이었다. 위상이 0초 근처면 오프셋(`%10`)이 0.04와 9.99로
갈려 일반 표준편차가 4.4~4.6초로 부풀려진다(실제 간격은 9.3~10.8초로
정상). 각 오프셋을 원 위의 각도로 보고 평균 벡터 길이로 산포를 재는
원형 표준편차로 바꿔 0.24~0.34초로 정상 판정 → **54/54**.

| 방식 | 1일차 54개 정상 |
|---|---|
| 임계값 (파라미터 전수 스윕 최적) | 7개 (13%) |
| 주기 누적 | 51개 (94%) |
| 주기 누적 + 원형 표준편차 판정 | **54개 (100%)** |

거리별로도 전부 성공(근거리 18/18, 중거리 18/18, 원거리 18/18).

|---|---|---|---|
| 1일차 | 아울렛 | 54/54 | 0.205초 |
| 2일차 | 아파트 | 54/54 | 0.143초 |
| 3일차 | 아파트 | 54/54 | 0.127초 |

**추가 4: 기존 파형 ▲를 새 검출기 결과로 교체** (2026-08-28)

`SourceWaveform.tsx`가 전대역 파형에서 "평균+2.5σ"로 직접 계산하던
피크 후보는 저역 소음(엔진·환기팬·음악)에 반응해 문 닫힘·차량 통과만
찍히고 정작 비프음은 놓쳤다. 이제 `getSourceBeepOnsets()` 결과를 그대로
쓴다 — **파형의 ▲와 비프 대역 탭의 빨간 세로선이 같은 지점**을 가리킨다.
검출 API가 실패해도 파형 자체는 그대로 렌더된다(표식만 안 뜸).

> 이 변경은 "기존 로직 수정 금지" 제약의 예외다 — 사용자가 직접
> "피크 후보가 상관없는 곳에 찍힌다, 제대로 고쳐라"고 지시했다.

**프론트**: `SourceList.tsx`의 기존 두 탭 토글에 세 번째 버튼("비프 대역
1.5~2.5k")만 추가, 클릭 시 신규 컴포넌트 `SourceBandSpectrogram.tsx`를
렌더(기존 `Spectrogram.tsx`는 import도 안 함). 1900/2100Hz 점선 가이드 +
검출 onset을 `status.error` 토큰 세로선으로 오버레이, 개수·오프셋
(onset%10)·중앙값·표준편차·간격을 텍스트로 함께 표시 — 오프셋이 5초
근방에 몰리고 표준편차 0.1초 이내면 "규칙적"(녹음 설계: 초의 일의
자리 5초에 키를 눌렀으므로 매 10초 구간 온셋이 전부 같은 위상이어야
함), 흩어지면 "불규칙"으로 경고해 k·대역폭 조정 신호를 준다.

**API**(둘 다 라벨 저장 없음, 표시 전용):
- `GET /source-files/{id}/band-spectrogram?fmin=&fmax=`
- `GET /source-files/{id}/beep-onsets?band_low_hz=&band_high_hz=&k=&k_global=&min_gap_sec=`

**검증**: 백엔드 테스트 29개(260/260 전체 통과) + 로컬 브라우저 +
**NAS 실서버 배포·확인**. 실데이터 최종 결과(`260818_001.WAV`):
검출 10개·오탐 0, 오프셋 표준편차 0.08초, 간격 9.80~10.14초 —
화면에 "규칙적 — 검출 정상으로 보임"으로 표시된다.

**실데이터 확보 방법(다음에도 쓸 것)**: 원본 wav를 통째로 받는 API가
없어서, **fixed_interval 데이터셋(10초 균일 조각)의 세그먼트 10개를
`/segments/{id}/audio`로 받아 이어붙여** 100초 원본을 복원했다.
event_detection 세그먼트(6초, 이벤트 주변만)로는 오탐 지점이 안 잘려
있어 분석이 안 된다.

**부수 관찰**: NAS 기존 `event_detection` 결과의 `detected_at`이
5.851·15.836·25.913초로, 사양(5·15·25초)보다 **일관되게 0.85~0.91초
늦다**. 오프셋(`%10`)이 5.84~5.91로 매우 일정하므로 검출 오류가 아니라
실제 비프음 위상이 밀린 것(녹음 시작 지연 등)으로 보인다 — 위상 규칙
GT를 쓸 때 "5.0초 고정"이 아니라 **파일별 오프셋 중앙값 기준**으로
판단해야 한다는 뜻.

**추가 7: 검출 지점 순음성 전수 측정 — 자동 통과율 ≠ 정확도** (2026-08-31)

교수님 질의("최종 결과가 다 잘 탐지됐다는 의미인가")에 답하려고 근거를
n=5 표본에서 **전수**로 확대했다. 세그먼트는 [검출±3초]이므로 **조각 중앙
= 검출 지점**, **양 끝 = 비검출 지점** — 같은 파일·같은 환경이라 조건이
통제된다. 2,160개 조각 전부에서 welch 스펙트럼 측정:

| | 표본 | 대역비 중앙값 | 피크 1975~2010Hz | 14dB 이상 |
|---|---|---|---|---|
| 검출 지점 | 2,160곳 | **+20.13 dB** | **80.1%** | **65.7%** |
| 비검출 지점 | 4,320곳 | +1.38 dB | 21.2% | 0.7% |

차이 +18.75dB, 파일 단위 211/216(97.7%)에서 검출 지점 우세.

**동시에 한계도 수치화됐다**: 검출 지점의 19.9%는 피크가 1992Hz 근처가
아니고, 34.3%는 순음성 14dB 미만이다. **검출 지점이 오히려 더 약한 파일이
5개** 있다(`2_260821_018`·`270821_006`·`260818_050`·`260819_044`·
`2_260821_015`) — 우선 검수 대상.

**교훈**: 주기 방식의 "216/216"은 **자동 기준(10개·위상 0.5초) 통과율이지
정답 대비 정확도가 아니다.** 주기 창마다 1개씩 고르는 구조라 신호가 없어도
통과할 수 있다(실제로 비프음 없는 5000~5400Hz에서 위상 편차 0.183초로 통과).
신호 근거로 본 실제 적중은 **80% 선**으로 보이며, 확정은 사람 청취가 필요하다.
보고서·문서에서 이 수치를 "정확도 100%"로 쓰지 말 것.

**추가 8: 비프 대역 탭에 대역통과 파형 연동** (2026-09-01)

사용자 지적 2건: ① "웨이브폼은 주파수 대역도 안 보인다" ② "세 번째 버튼으로
확대한 게 웨이브폼엔 적용이 안 된 것 같다". 둘 다 사실이었다.

**원인 1 — 파형이 실제로 안 보였다.** `SourceWaveform`이 절대 스케일로
그리는데(`peaks[i] * (height-4)`) 본수집 녹음 레벨이 -63dBFS라 뭉갠다.
실측(`260818_001.WAV`, height=120px):

| | 최대 막대 | 중앙값 | 0.5px 이하 |
|---|---|---|---|
| 기존 전대역(절대) | **1.14px** | 0.30px | **98.7%** |

NAS 실세그먼트 3개를 이어붙인 신호에서는 더 심했다 — 최대 0.13px, **100%가
0.5px 이하**. 화면에는 가운데 가로줄만 보인다.

**원인 2 — 탭이 파형에 연결돼 있지 않았다.** `SourceList`에서 파형이
`view` 상태 **바깥**에 있어, 탭은 아래 스펙트로그램만 바꾸고 파형은 항상
전대역이었다. ▲만 대역통과 검출기 결과라 **표식과 막대가 서로 다른 것을
가리키는** 상태였다.

**해결**: 신규 파일 `audio/band_waveform.py` + `GET
/api/source-files/{id}/band-waveform`. 검출기와 **같은 대역통과·같은 모노화**
(`to_mono(..., channel="mean")`)를 쓰고 Hilbert 엔벨로프를 자기 최대값으로
정규화한다. 프론트는 `SourceWaveform`에 **opt-in `band` prop**(기본 false)을
두어 비프 대역 탭에서만 켠다 — **기존 두 탭의 표시는 100% 동일**하다.

효과(같은 실데이터, height=120px):

| | 최대 막대 | 중앙값 | 0.5px 이하 |
|---|---|---|---|
| 기존 전대역(절대) | 0.13px | 0.03px | 100.0% |
| **신규 대역통과(정규화)** | **116.00px** | 1.01px | **34.8%** |

**주의**: 정규화라 **파일 간 절대 크기 비교 불가**. `peak_abs`(실제 최대
진폭)를 응답과 화면에 함께 실어 원래 레벨을 잃지 않게 했고, 절대 비교는
기존 "실제 크기" 탭을 쓰도록 안내 문구를 붙였다.

**교훈**: "파형에 주파수가 안 보인다"는 파형의 원리적 한계(세로축=진폭)라
고칠 수 없지만, **그 지적이 나온 진짜 이유는 파형이 아예 안 보였기
때문**이었다. 사용자 표현을 그대로 요구사항으로 받지 말고 화면에서 실제로
무엇이 보이는지 수치로 재볼 것.

**추가 9: 비프 대역 탭에 Hz 축 추가** (2026-09-02)

사용자 요청("시각화에 헤르츠 대역 보이게 해라"). 비프 대역 탭에는 Hz
눈금이 **아예 없었다** — 1900/2100Hz 점선만 있어 무늬가 보여도 그게 몇
Hz인지 읽을 수 없었다. (기존 두 탭은 `showAxis`로 이미 축이 있어 무수정.)

- `pickBandTicks()`: 크롭 대역에 **선형** 눈금(멜과 달리 위치 계산이 단순).
  200Hz 간격 기본, 대역이 좁아지면 100Hz까지 촘촘해진다.
- 라벨은 기존 `formatHz()` 재사용 — 두 스펙트로그램의 표기가 일치한다.
- 눈금선은 `white/20`, 1900/2100Hz 가이드는 `white/40` 점선으로 남겨 구분.

**함정: 축을 붙이면 시간축이 어긋난다.** Hz 라벨 영역(`w-11` + gap = 48px)
만큼 스펙트로그램이 오른쪽으로 밀리는데 위의 파형은 안 밀린다. 두 그림의
0초·100초가 어긋나면 "이 봉우리가 저 무늬"라는 대응이 틀리게 보인다.
SourceList에서 비프 대역 탭일 때만 파형에 같은 `pl-[48px]`을 준다.
**실측 검증**: 파형·스펙트로그램 캔버스의 좌측 좌표 차이 0px(브라우저).

라벨과 눈금선을 **같은 높이 기준**(캔버스 height)에 두는 것은 기존
Spectrogram.tsx에서 실측된 함정과 동일 — `items-stretch`를 주면 라벨
영역이 캔버스보다 커져 어긋난다. 같은 구조를 그대로 따랐다.

**후속 수정(같은 날)**: 위 "시간축 0px" 검증은 **캔버스만 잰 것이었고,
시간 라벨은 어긋나 있었다.** 사용자 지적("스펙트로그램에 초가 안맞아")으로
발견. 라벨 줄이 컨테이너 전체(Hz축 48 + 캔버스 760 + "Hz" 접미사)에
`justify-between`으로 퍼져, `100초`가 캔버스 오른쪽 끝보다 **203px
바깥**(1042 vs 839)에 찍혔다. `pl-12`로 왼쪽만 막아 오른쪽이 새던 것.

수정: 라벨 줄을 캔버스와 **같은 폭·같은 시작점**에 가두고, 각자
하드코딩하던 48을 `HZ_AXIS_PX` 상수로 공유(SourceList의 파형 들여쓰기와
같은 값을 쓰지 않으면 또 어긋난다). 실측 재검증: 0초·100초 라벨 모두
파형과 **0px 차이**.

**교훈**: 정렬을 검증할 때 **사용자가 실제로 보는 요소**를 재야 한다.
캔버스가 맞아도 라벨이 틀리면 화면은 어긋나 보인다. 눈금이 붙은 그림을
위아래로 겹칠 때는 캔버스·눈금선·축 라벨을 **각각** 확인할 것.
